## Project

KDE Dolphin file manager (Qt6 / KDE Frameworks 6, C++20, CMake + ECM). This checkout is the base for the fork "Orcinus" (working title and internal code name "Whale": `src/whale/`, `Whale*` classes, `WHALE_*` CMake variables, `whale_*` action names and the local build directories keep it; see `.privatedoc/orcinus-rename-plan.md`): `origin` = github.com/Arkarit/whale, `upstream` = invent.kde.org/system/dolphin. Upstream changes are merged via `git fetch upstream`.

## Build, run, test

There are two out-of-tree builds. The existing Dolphin/KDevelop build must not be reconfigured;
Orcinus development uses its own build and private install prefix:

- Dolphin build (do not touch): `/home/user/Projects/_external/kde/build-dolphin`
- Whale build: `/home/user/Projects/_external/kde/build-whale` (Ninja, `RelWithDebInfo`, `BUILD_TESTING=ON`)
- Whale install prefix: `/home/user/Desktop/Home/Projects/_external/kde/install-whale`

```bash
cmake --build ../build-whale                        # build everything
cmake --build ../build-whale --target dolphin       # target remains internally named dolphin
ctest --test-dir ../build-whale --output-on-failure # all tests
ctest --test-dir ../build-whale -R kfileitemmodeltest
../build-whale/bin/kfileitemmodeltest someTestFn    # run one QTest function directly
```

Alternatively `CMakePresets.json` provides in-tree presets (`dev`, `asan`, `unity`, …; `cmake --preset dev`), which build into `./build*`.

Running the dev build: `source ../build-whale/prefix.sh && ../build-whale/bin/orcinus --new-window`.
Orcinus has an independent D-Bus identity, so it cannot hand URLs to Dolphin. `--new-window`
remains useful while developing because it bypasses Orcinus's own running instance.

Phase 1 deliberately reuses the system `libdolphinvcs.so.6`, VCS plugins, service menus, and
Dolphin handbook. Do not rename the `dolphin/vcs` plugin namespace or the per-folder `[Dolphin]`
view-properties group. The safe defaults are `WHALE_PROVIDE_FILEMANAGER1=OFF`,
`WHALE_INSTALL_DOLPHIN_EXTRAS=OFF`, and disabled KUserFeedback.

Tests are QTest-based, registered with `ecm_add_test` in `src/tests/CMakeLists.txt`; some need Baloo or a Ruby `test-unit` gem and are only added when found. `appiumtests/` holds Selenium/AT-SPI UI tests (see `appiumtests/Readme.md`, run via `selenium-webdriver-at-spi-run`).

Formatting: KDE clang-format style (`.clang-format`, generated by ECM, don't edit); CI also runs clang-format, REUSE (SPDX headers required on every file), XML/YAML/JSON lint. Commits prefixed `GIT_SILENT` are translation/script syncs from KDE infrastructure.

## Architecture

### Build targets (`src/CMakeLists.txt`)
- `dolphinprivate` (shared lib, installed as `liborcinusprivate`): the item-view framework (`kitemviews/`), `DolphinView` and everything in `views/`, view-related settings. Exported with `DOLPHIN_EXPORT`; the unit tests and the KPart link against it.
- `dolphinvcs` (shared lib): public plugin API `KVersionControlPlugin` for version-control integration. It is built for tests but not installed by default; installed Orcinus uses the ABI-compatible system library and `dolphin/vcs` plugins.
- `dolphinpart` (KPart plugin): embeds a `DolphinView` in other apps (e.g. Konqueror). It is not installed by Orcinus's safe defaults.
- `dolphinstatic` (static lib): the application shell: main window, tabs, panels, search, settings dialogs, selection mode, admin mode, etc.
- `dolphin` (executable, output name `orcinus`): `main.cpp` plus the optional `DBusInterface` (`org.freedesktop.FileManager1`), linking the two libs above.
- KCMs `kcm_dolphinviewmodes` / `kcm_dolphingeneral`, the service-menu installer, and kconf_update helpers are retained as build targets but not installed by default.

### Widget hierarchy
`DolphinMainWindow` → `DolphinTabWidget` → `DolphinTabPage` (one or two views in a splitter for split view) → `DolphinViewContainer` (URL navigator, filter bar, search bar, status bar, message widgets around a view) → `DolphinView` (the actual file view, independent of the main window so it can be reused by the KPart). Menus/actions are declared in `dolphinui.rc` (KXMLGUI); `DolphinViewActionHandler` wires view actions.

### `kitemviews/` – custom model/view framework (not Qt's QAbstractItemView)
Built on `QGraphicsView`, for performance and animations:
- `KItemModelBase` / `KFileItemModel`: flat model of `KFileItem`s fed by `KDirLister` (KIO). Handles sorting (`private/kfileitemmodelsortalgorithm.h`, parallel merge sort), filtering, grouping, and expansion in the details/tree view. Items are identified by index plus a role→QVariant hash.
- `KFileItemModelRolesUpdater`: asynchronously fills expensive roles (previews via KIO thumbnails, MIME icons, directory item counts, Baloo metadata) for visible items first.
- `KItemListView` / `KFileItemListView` / `KStandardItemListView`: layout (`private/kitemlistviewlayouter`), recycled `KItemListWidget`s, animations, group headers. The Icons/Compact/Details view modes are layout variants of the same view.
- `KItemListController`: all mouse/keyboard/drag interaction; `KItemListSelectionManager` holds selection (`KItemSet`/`KItemRange`).
- `KItemListContainer`: the QAbstractScrollArea hosting the view, smooth scrolling.
- `views/DolphinItemListView` and `DolphinFileItemListWidget` are the Dolphin-specific subclasses (zoom levels, version-control overlays).

### Settings
Global settings are KConfigXT: `*.kcfg` + `*.kcfgc` files generate the `*Settings` singleton classes at build time (e.g. `GeneralSettings`, `DetailsModeSettings`). Per-folder view properties (`views/viewproperties.cpp`) are stored in extended attributes via `KFileMetaData::UserMetaData`, falling back to `.directory` files or a global location. Schema migrations are `.upd` files plus small helper executables/scripts in `src/settings/`.

### Other areas
- `panels/`: dock panels (Places, Folders tree, Information, Terminal via KonsolePart), all subclasses of `Panel`.
- `search/`: search bar and query building (`DolphinQuery`), Baloo or filename/content search through KIO.
- `selectionmode/`, `admin/` (the "Act as Administrator" mode via kio-admin), `trash/`, `itemactions/` (context-menu plugins), `statusbar/`, `filterbar/`, `userfeedback/` (optional KUserFeedback telemetry).
- Optional features are behind `HAVE_BALOO`, `HAVE_KUSERFEEDBACK`, `HAVE_PACKAGEKIT`, `HAVE_X11`, etc. (`config-dolphin.h.cmake`).
- User-visible strings use KI18n (`i18nc` with context); `src/Messages.sh` extracts them. Logging via `qCDebug(DolphinDebug)`; `dolphindebug.h` is generated by `ecm_qt_declare_logging_category` in the build dir.

## Development philosophy (from README.md)
Dolphin focuses on usability for its target users ("Lisa", an office user, and "Simon", a power user managing files and FTP). Features and options that don't serve them are only acceptable if they are non-intrusive, i.e. they don't clutter the main menu, context menus or toolbar.
